📥
Checkout
Clona el repositorio en el runner
GitHub Actions clona tu repo en una máquina virtual Ubuntu limpia. Sin este paso no hay código que ejecutar.
uses: actions/checkout@v4
🟢
Setup Node.js 22
Instala la versión exacta de Node
Fija la versión de Node a 22 para que el entorno de CI sea idéntico al de producción. Evita bugs de compatibilidad.
uses: actions/setup-node@v4 with: node-version: 22
📦
Install dependencies
npm install limpio
Elimina el lockfile antes de instalar para evitar conflictos entre la versión local y el runner. Instala todas las dependencias desde cero.
rm -f package-lock.json npm install

deploy-azure.yml — despliegue continuo
CD Build & Deploy → Azure ubuntu-latest · Node 22
📥
Checkout
Clona el repositorio
Igual que en CI: clona el repo en un runner Ubuntu limpio, independiente del que corre CI.
uses: actions/checkout@v4
🟢
Setup Node.js 22
Misma versión que CI y producción
Paridad de entornos: CI, CD y Azure App Service usan Node 22 para evitar diferencias de comportamiento.
uses: actions/setup-node@v4 with: node-version: 22
📦
Install dependencies
Instala paquetes para el build de producción
Instala todas las dependencias necesarias para compilar. El resultado del build será standalone y no necesitará node_modules en producción.
rm -f package-lock.json npm install
🏗️
Build de producción
Compila Next.js en modo standalone
El modo standalone genera una carpeta autocontenida con todo lo necesario para correr la app sin node_modules. Reduce el tamaño del deploy drásticamente.
npm run build
🔒 DATABASE_URL 🔒 JWT_SECRET
📁
Prepare deployment package
Arma la carpeta ./deploy lista para subir
Copia las tres partes necesarias del build a una sola carpeta ./deploy:
# App standalone (servidor Node) cp -r .next/standalone ./deploy # Assets estáticos (CSS, JS, imágenes) cp -r .next/static ./deploy/.next/static # Archivos públicos (logo, favicons) cp -r public ./deploy/public
☁️
Deploy to Azure App Service
Sube el paquete a Azure y reinicia la app
La action oficial de Azure sube ./deploy al App Service usando el Publish Profile. Azure reinicia automáticamente el servidor y la nueva versión queda activa en snackiverse.co.
uses: azure/webapps-deploy@v3 with: app-name: ${{ secrets.AZURE_APP_NAME }} publish-profile: ${{ secrets.AZURE_PUBLISH_PROFILE }} package: ./deploy
🔒 AZURE_APP_NAME 🔒 AZURE_PUBLISH_PROFILE
✓ snackiverse.co actualizado ✗ Versión anterior sigue activa
⚠️ CI y CD corren en paralelo cuando hay push a main. Eso significa que el deploy puede llegar a Azure antes de que los tests terminen. Si un test falla después, el código roto ya está en producción. Para un proyecto en producción real lo ideal es encadenar CD después de CI.

📤
Recibe el paquete
Azure recibe la carpeta ./deploy vía Publish Profile.
El Publish Profile es un XML con credenciales de deploy descargado desde el portal de Azure. La action de GitHub lo usa para autenticarse y subir los archivos por FTP/WebDeploy.
▶️
Inicia la app
Ejecuta node server.js del standalone build.
Next.js en modo standalone genera un server.js que levanta la app completa. Azure lo ejecuta automáticamente al terminar el deploy. No necesita npm install ni node_modules en el servidor.

Sirve en snackiverse.co
Dominio personalizado con SSL apuntando al App Service.
DNS en Porkbun: registro A @ → 13.89.172.9. Certificado SSL administrado por Azure (gratis, auto-renovable). También disponible en www.snackiverse.co.
🔌
Conecta a Neon (PostgreSQL)
DATABASE_URL apunta a la BD en la nube de Neon.
Neon es un servicio de PostgreSQL serverless. La cadena de conexión incluye host, puerto, usuario, contraseña y nombre de la BD. Se configura en Azure Portal → Configuración → Variables de aplicación.
🔒
Variables de entorno
DATABASE_URL y JWT_SECRET definidas en Azure Portal.
En Azure: App Service → Configuración → Variables de aplicación. Estas variables reemplazan al archivo .env en producción. Nunca se suben al repositorio de GitHub.

🔒 GitHub Secrets — click para ver dónde configurar cada uno
DATABASE_URL
Conexión a PostgreSQL en Neon. Usada en build (CI y CD).
Formato:
postgresql://user:pass@host/db?sslmode=require

Dónde configurar: GitHub → Settings → Secrets and variables → Actions → New repository secret.

También en: Azure Portal → App Service → Configuración → Variables de aplicación.
JWT_SECRET
Firma los tokens JWT de sesión. Debe ser igual en CI y Azure.
Requisito: Cadena larga y aleatoria (mínimo 32 caracteres). Si cambia, todos los usuarios quedan deslogueados.

Dónde configurar: GitHub Secrets + Azure Variables de aplicación. Los dos valores deben ser idénticos.
AZURE_APP_NAME
Nombre del App Service en Azure. Identifica dónde desplegar.
Valor: snackiverse (el nombre que aparece en el portal de Azure).

Dónde ver: Azure Portal → App Services → nombre del recurso en la parte superior izquierda.
AZURE_PUBLISH_PROFILE
XML con credenciales de deploy. Se descarga desde Azure Portal.
Cómo obtenerlo: Azure Portal → App Service → botón "Obtener perfil de publicación" (en la barra superior). Descarga un archivo XML.

Cómo guardarlo: Copiar todo el contenido del XML y pegarlo en el valor del secret en GitHub. Incluye credenciales de FTP y WebDeploy.
